## The synthetic problem

The fictional user is an analyst prioritizing a **synthetic** equipment-review queue.
At one reading, the model receives temperature, vibration, load, and machine type.
It predicts whether a simulated next shift receives a review label.
The output is a review probability and a fixed-threshold routing suggestion.

This is **not a validated maintenance or equipment-safety system**.
No real equipment data, physical failure model, or safety claim is involved.
The measurements and labels are generated by a small inspectable program.
The scenario supplies engineering constraints, not domain authority.

The target is named `synthetic_next_shift_review`.
It is a noisy binary event, not an observed real-world failure.
Features are available at prediction time; the target is not.
The unit ID exists only for partitioning and audit, never as a model feature.

## Input contract

Every prediction record has exactly these fields:

| Field | Meaning | Accepted reference range |
|---|---|---|
| `temperature_c` | synthetic temperature measurement | 0 through 150, or null |
| `vibration_mm_s` | synthetic vibration measurement | 0 through 30, or null |
| `load_pct` | synthetic load percentage | 0 through 100, or null |
| `machine_type` | categorical machine label | trimmed nonempty string, at most 64 characters |

Ranges are application contracts, not empirically validated operating limits.
Numeric null is allowed and means an explicitly missing measurement.
A missing **field** is rejected because it could indicate schema drift.
Unknown nonempty machine-type strings are accepted and flagged at inference.
Numeric strings, booleans, NaN, infinity, and out-of-range values are rejected.
Unexpected fields are rejected instead of silently discarded.

The reserved category spelling `<unknown>` is internal and cannot be supplied literally.
Category matching is case-sensitive; there is no undocumented lowercasing policy.
Inference batches must contain 1 through 128 records.
An empty request is an error, not an empty success-shaped prediction.

## Data generator walkthrough

There are 200 fictional units, each with six correlated readings.
Training uses units 0–119: 720 readings.
Validation uses units 120–159: 240 readings.
Final test reserves units 160–199: 240 readings.

`SPLIT_UNITS` stores disjoint Python `range` objects.
`make_split(name)` loops only through the range for the requested partition.
Each unit gets its own `random.Random(9000 + unit)` instance.
Generation does not depend on which other split was requested first.

Machine type cycles among pump, fan, and compressor.
A per-unit temperature offset, vibration offset, and hidden risk make repeated readings correlated.
Each reading also has its own random measurements and event draw.
Splitting individual readings would leak unit-specific structure into evaluation.
Holding out units matches the stated new-unit deployment question better.

The risk logit contains normalized temperature, vibration, load, and category effects.
It also contains an extra interaction when vibration exceeds 2.8 and load exceeds 70.
That interaction motivates trying one nonlinear model.
A hidden unit effect and a Bernoulli draw make labels noisy.
Even access to the visible generator formula cannot make every label predictable.

About 6% of each numeric field is independently replaced with null after label generation.
Missingness therefore removes information that helped generate the label.
Imputation cannot recover that exact lost measurement.
The missingness mechanism is authored for this exercise, not inferred from real sensors.

Each generated row contains `unit_id`, `inputs`, and `target`.
Only `inputs` reaches preprocessing.
The target becomes a separate floating tensor for BCE.
The unit ID is never encoded into the network.

## Completed experiment contract

The predeclared candidates are:

1. Logistic binary classifier, weight decay 0.001.
2. One-hidden-layer width-16 ReLU network, weight decay 0.002.

Both use train-only preprocessing, seed 5054, Adam lr 0.025, and 160 full-batch updates.
Neither uses adaptive early stopping or a search over hidden widths.
Each receives the same training and validation rows.
Selection uses the lowest **validation BCE**; the first declared candidate breaks exact ties.
The probability decision threshold stays fixed at 0.5.

The reference engineering budget is CPU/offline, at most 250 trainable parameters,
and at most 128 records per inference request.
This is a functional budget, not a measured production latency guarantee.
Tiny loops use one PyTorch CPU thread to avoid unnecessary scheduling overhead.

The educational final-score goal is BCE at most 0.58 and balanced accuracy at least 0.68.
These numbers are predeclared exercise targets, not domain acceptance standards.
Missing a goal must be reported honestly.
It does not authorize retuning on the final test.

## What this session does and does not run

The script constructs training and validation only.
It asserts their unit-ID sets are disjoint.
It prints one training row and the observed development class fractions.
It prints the frozen candidate and evaluation contract.
It does **not** construct or inspect test rows.

Specifying the test unit range and count is allowed before evaluation.
Using its measured outcomes to change a candidate is not.
The test first enters a scoring path after selection is persisted in session 53.

## Controlled experiments

### A. Propose a reading-level split

Predict: the same unit's latent effects can occur on both sides of the split.
Explain why an apparently stronger score would answer a different, easier question.
Keep the reference unit split for the final experiment.

### B. Tighten the parameter budget below 100

Predict: the 193-parameter nonlinear candidate becomes inadmissible.
The 11-parameter logistic baseline remains feasible.
Constraints can determine the candidate pool before score optimization.

### C. Make missing values illegal

Predict: the generator now produces records your inference schema rejects.
You must either change data collection or explicitly handle missingness.
Do not let training silently accept inputs that deployment rejects.

## Checkpoint questions

<details>
<summary>Why use a synthetic problem after so many substantive sessions?</summary>

It makes the entire pipeline runnable offline and its data-generating assumptions inspectable.
The engineering workflow is real; the domain evidence is not.
That distinction must remain visible in every claimed result.
</details>

<details>
<summary>Why not pick the model with the best final-test score?</summary>

That would turn the final test into another validation set.
Choose using development evidence, freeze the decision, and evaluate that choice once.
If the result disappoints, report the disappointment and plan a new evaluation.
</details>

<details>
<summary>Why save preprocessing instead of recomputing it during inference?</summary>

New requests are not the training distribution and must not refit the feature mapping.
The trained weights expect an exact feature order, category vocabulary, means, and scales.
Those are part of the deployed model, not disposable training conveniences.
</details>

## Design judgment

A well-scoped capstone is a complete decision pipeline with a defensible claim.
Novelty here is the integrated task, not a novel neural architecture.
The simplest winning model is an acceptable and informative final result.
