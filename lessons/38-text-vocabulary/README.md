## The problem

An embedding accepts integer indices, not strings.
We need a repeatable function from an inspectable message to a sequence of IDs.
We also need a policy for a word that was absent during fitting.
Learning a vocabulary from all available messages would quietly use held-out information.
Even without labels, that would change the representation using the evaluation distribution.

Our data is an intentionally tiny **synthetic** service-message fixture.
Label 1 accompanies words such as `good`, `bright`, `helpful`, and `friendly`.
Label 0 accompanies words such as `bad`, `dull`, `rude`, and `slow`.
These are authored toy rules, not an annotation study of human sentiment.
There are 24 training messages, 8 validation messages, and 8 final-test messages.
The split lists are explicit, not regenerated by an unrecorded random shuffle.

## Read the helper in execution order

1. `TEXT_SPLITS` is a dictionary whose values are lists of `(text, label)` tuples.
2. `tokenize(text)` lowercases the string and then splits on whitespace.
3. `make_vocab(training_texts)` extracts the distinct training words.
4. It sorts those words, making IDs independent of training-list iteration order.
5. It reserves two entries before assigning ordinary-word IDs.
6. `encode(text, vocabulary)` looks up every token, preserving sequence order.

The tokenizer maps `"GOOD service"` to `["good", "service"]`.
It does **not** remove punctuation, understand morphology, or recognize negation.
For example, `"good!"` and `"good"` are different tokens here.
That limitation is deliberate: the full preprocessing policy fits on one line.

The set comprehension
`{word for text in training_texts for word in tokenize(text)}`
is two nested loops that collect unique words.
It does not retain counts or labels.
`sorted(...)` returns a list with a deterministic lexical ordering.
`enumerate(words, start=2)` yields `(2, first_word)`, `(3, second_word)`, and so on.

The dictionary unpacking expression `**{...}` inserts those word/ID pairs into
the dictionary that already contains the two reserved entries.
This is ordinary Python construction, not a PyTorch operation.
Labels never participate in vocabulary fitting.

## Why two reserved IDs?

`PAD = 0` means “this batch cell is not part of the original sequence.”
`UNK = 1` means “a real input token exists here, but its spelling was not fitted.”
Neither is an ordinal score, and their different meanings matter later.

Consider a three-token input containing one unseen word.
The unknown word still occupies a real sequence position.
When averaging embeddings, it must count toward the denominator.
Padding inserted to make a rectangular batch must not count.
Conflating PAD and UNK would make missing vocabulary look like shorter input.

The helper uses `vocabulary.get(word, UNK)`.
Dictionary `get` returns the fallback instead of raising `KeyError`.
It does not extend the dictionary.
Vocabulary growth at validation or inference time would invalidate embedding-row alignment.

The fixture has no literal reserved-marker words.
`<pad>` and `<unk>` are internal sentinels, not a general escaping/tokenization protocol.
A production tokenizer needs a documented treatment of literal special-token strings.

## Follow `main`

The training texts are selected with `[text for text, _ in train]`.
Here `_` is the conventional name for a value intentionally not used.
Only that list is passed to `make_vocab`.

For each held-out split, the script prints words missing from the fitted dictionary.
`weekend` appears in validation, and `evening` appears in test.
Neither is added to the vocabulary.
Seeing a held-out **word audit** here is a preprocessing demonstration, not a tuning loop.
Do not change the vocabulary based on which held-out words make a model score better.

The executable assertions establish four contracts:

- PAD and UNK have distinct IDs.
- Encoding is case-normalized by the documented tokenizer.
- Unseen words receive UNK without changing the fitted dictionary.
- Reversing training-row order leaves the fitted mapping unchanged.

Whitespace-only input currently encodes as an empty Python list.
That is an explicit intermediate representation, not permission to average zero tokens.
Session 39 will reject empty sequences at collation/pooling boundaries.

## Shapes before tensors

`"helpful unfamiliar service"` becomes a Python list of length 3.
Another message may become a list of length 2.
These ragged lists cannot yet form one ordinary rectangular integer tensor.
That is the batching problem in session 39.
Eventually IDs will have shape `[batch, tokens]` and dtype `torch.long`.
Embeddings will add a final feature dimension.

## Controlled experiments

### A. Add an unseen word to validation only

Edit one validation message to include `spectacular`.
Predict: the printed validation unknown-word list gains that word.
Predict: training vocabulary IDs and size remain unchanged.
Run and compare the printed mapping.
If it changes, held-out text has entered the fitting path.

### B. Add a word to training only

Add `spectacular` to one training message instead.
Predict: vocabulary size increases by one.
IDs after its alphabetical position may shift because construction sorts words.
That is why a vocabulary must be saved with any weights trained against it.
An embedding matrix alone cannot tell you which spelling each row represented.

### C. Change capitalization and punctuation

Try `"GOOD service"` and `"good! service"` in the final encoding print.
Predict: capitalization is removed, punctuation is not.
Interpret the result as a preprocessing contract, not as model intelligence.
Restore the fixture after these experiments before continuing.

## Checkpoint questions

<details>
<summary>Why is an unlabeled validation vocabulary still a leak?</summary>

It lets evaluation inputs change the fitted representation.
Knowing which spellings will occur affects unknown-token frequency and embedding size.
The deployment contract should be determined from training data and a predeclared tokenizer.
</details>

<details>
<summary>Could PAD and UNK share a zero-valued vector?</summary>

Their vectors could happen to have equal values, but their identities must stay distinct.
A mask excludes PAD positions while keeping UNK positions.
Equal numeric vectors do not justify equal masking semantics.
</details>

<details>
<summary>Does sorted vocabulary construction make training reproducible?</summary>

It makes this one preprocessing step deterministic.
Model initialization, data order, optimizer settings, and the execution environment still matter.
It also cannot preserve old IDs after adding a new training word.
</details>

## Design judgment and limits

Word-level whitespace tokenization is inspectable but has a large unknown-word problem.
Subword tokenizers offer another tradeoff but require their own fitted artifacts and contracts.
Do not introduce one merely to hide the decisions demonstrated here.
This synthetic fixture supports reasoning about data flow, not real NLP quality claims.
Next, build a batch without allowing rectangular padding to change its meaning.
